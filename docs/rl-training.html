Training the RL Dynamic-Obstacle Avoidance Policy from Scratch

This page documents the full RL training pipeline — ScanHistoryTransformerActor architecture, 1176-dim observation design, 20+ reward terms, adaptive obstacle curriculum, domain randomization, and integration into the Nav2 local control pipeline for ROSMASTER M3.

Why This Page Exists

RL training is the main engineering contribution

The classical controllers (DWB, MPPI, RPP) are existing Nav2 baselines. The RL controller is different because it is designed, trained, and validated entirely as part of this project.

This page documents every design decision: why a transformer over lidar rays instead of a flat MLP, how the observation space splits policy from privileged critic information, what each of the 20+ reward terms does, how the curriculum stages obstacle difficulty before introducing sensor noise and actuator delays, and how the final policy is exported and loaded into the Nav2 local controller interface.

Actor Architecture

ScanHistoryTransformerActor

Instead of processing each lidar snapshot independently, the actor treats each of the 144 lidar rays as a token whose value is an 8-frame temporal history. This lets the transformer learn ray-wise closing motion — detecting which specific angular sectors contain obstacles that are approaching — without ever receiving explicit obstacle positions or velocities.

The critic, by contrast, receives ground-truth positions and velocities of the 4 nearest dynamic obstacles as privileged information during training, allowing better value estimation without leaking this information to the deployed policy.

Critic Network

  • Simple MLP: Linear(1209→256)→ELU→Linear(256→256)→ELU→Linear(256→128)→ELU→Linear(128→1)
  • Receives full 1209-dim privileged observation including dynamic obstacle states
  • Outputs scalar value estimate — not deployed, training-time only

Noise and Distribution

  • Scalar learnable std parameter, initialized to 0.3
  • Action distribution: Normal(mean, std)
  • Sampling during training, deterministic mean at inference
  • Std clamped ≥ 1e-6 to prevent collapse

Observation Space

The policy never receives raw obstacle positions or velocities — it must infer obstacle motion from lidar history alone. The critic receives privileged ground-truth obstacle information during training to produce accurate value estimates, without this information leaking to the deployed policy.

Action Space

3D mecanum velocity command

The policy outputs a 3D velocity command that maps directly to ROSMASTER M3's mecanum wheel configuration. Lateral velocity (vy) enables the robot to strafe sideways — a capability absent in differential-drive robots that the RL policy can learn to exploit for more elegant obstacle avoidance without rotating in place.

Actions are clipped to [−1, 1] by the actor head, then scaled by the per-axis limits. A rate limiter enforces smooth acceleration by clamping the change per step. A static map action shield can override the command if it would drive into a known wall.

Velocity Limits

  • Forward: vx ∈ [−0.5, +0.5] m/s
  • Lateral: vy ∈ [−0.5, +0.5] m/s
  • Yaw: wz ∈ [−1.5, +1.5] rad/s

Rate Limits (per RL step, 33 ms)

  • Δvx: ± 0.025 m/s
  • Δvy: ± 0.025 m/s
  • Δwz: ± 0.08 rad/s

Action Processing Pipeline

  • Clip to [−1, 1] → scale by limits
  • Apply action delay buffer (domain randomization)
  • Apply motor strength scaling (domain randomization)
  • Apply rate limiter (smooth acceleration)
  • Apply static map shield (block wall-collision commands)
  • Convert to wheel velocities via mecanum kinematics

Reward Design

20+ terms covering path following, obstacle avoidance, and behavior shaping

The reward function balances path-following, obstacle avoidance, goal reaching, and action regularity. Dynamic obstacle rewards use only information available to the critic (obstacle states) to shape the value function, while the policy learns avoidance from the scan history alone. Behavioral shaping terms prevent degenerate strategies such as spinning in place or waiting indefinitely.

Path Following

Reward TermWeightDescription
progress +35.0 Increase in cumulative arc-length progress along Nav2 path per step, clamped to [−0.05, +0.05] m
goal_approach +5.0 Decrease in Euclidean distance to the final goal waypoint per step, clamped to [−0.08, +0.08] m
cross_track −4.0 Penalty proportional to cross-track error (lateral distance from path), clamped to [0, 1.0] m
path_rejoin +15.0 Reward for reducing cross-track error when CTE > 0.2 m — encourages returning to path after bypass
heading_alignment +8.0 cos(path_tangent_heading − robot_yaw) evaluated 4 steps ahead on the path lookahead
path_velocity +6.0 Robot velocity projected onto path tangent direction, normalized by max_vx

Curriculum Design

Obstacles mastered before domain randomization

The curriculum follows an obstacles_first strategy: the policy must first learn to handle increasingly difficult obstacle configurations before sensor noise and actuator imperfections are introduced. Promotion and demotion thresholds are evaluated continuously over a rolling performance window, ensuring stable progression without premature advancement.

Training Environment

IsaacLab / Isaac Sim setup

Simulation

IsaacLab / Isaac Sim with PhysX TGS solver. Multiple parallel environments for efficient rollout collection. Physics at 120 Hz, RL step every 4 physics steps (33 ms effective control rate).

Navigation Data

Real Nav2 path data from ROSMASTER M3 navigation runs in an AWS warehouse map. Up to 600 path points per episode, randomly sampled each reset. Static occupancy map used for action shielding and reward computation.

Robot Model

ROSMASTER M3 with 4 mecanum wheels (0.035 m radius, wheelbase 0.0795 m × 0.0978 m). Root velocity applied directly during training; converted to wheel velocities for deployment.

Episode Configuration

  • Fixed time limit; terminated early on success, collision, or stuck detection
  • Start: robot placed at path start with small yaw noise
  • Goal: final Nav2 path waypoint, success threshold 0.3 m
  • Stuck detection: near-zero speed for an extended period terminates episode

Lidar Sensor

  • 360° scan, 144 rays uniformly spaced (2.5° resolution)
  • Max range: 10 m; step resolution: 0.1 m
  • 8-frame rolling history maintained per environment
  • Normalized to [0, 1] before feeding the actor; clamped at 4 m

Domain Randomization

Sim-to-real transfer preparation

Sensor Noise

Lidar ray count degradation, Gaussian range noise, random ray dropout (simulating sensor blind spots and interference in real warehouse environments).

Actuator Imperfections

Action delay (1–3 step command buffer), per-wheel motor strength scaling (uneven drive), left/right wheel slip coupling (friction loss on one side).

Physical Parameters

Robot mass variations, center-of-mass shifts, wheel radius mismatch between left and right sides — covering manufacturing tolerances of the real ROSMASTER M3.

Domain randomization is applied after the policy reaches competence at each obstacle curriculum level, ensuring the policy first learns stable navigation before adapting to physical perturbations.

Connection to Benchmark

How the trained policy is evaluated

After training, the policy checkpoint is loaded by a ROS 2 node that implements the Nav2 local controller plugin interface. On each control tick, it assembles the 1176-dim observation from Nav2 path data, lidar scan history, and odometry, runs a forward pass through the ScanHistoryTransformerActor, and publishes the resulting [vx, vy, wz] command on /cmd_vel.

This keeps the benchmark fair: DWB, MPPI, and RPP use their standard Nav2 implementations, while the RL controller uses the trained policy produced by this pipeline — all evaluated under the same ROSMASTER M3 scenarios and metrics.
